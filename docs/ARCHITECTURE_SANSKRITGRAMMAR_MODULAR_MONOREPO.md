# Architecture — SanskritGrammar modular monorepo

_Created: 29-07-2026 · Last updated: 29-07-2026_

_Provenance: root best-effort after the configured Fable Planner returned no draft. This document is not advisor-approved._

This document defines the target architecture for modernizing SanskritGrammar as a modular monorepo. It is a planning artifact, not an implementation claim. The binding outcome is one repository with explicit application, tooling, content, data, pipeline, and test boundaries; Docusaurus remains the publication application; content remains auto-discovered without a publication manifest.

## 2. Binding architecture rulings

The following rulings are settled:

1. SanskritGrammar becomes a modular monorepo, not a collection of separately versioned repositories.
2. Docusaurus remains the site platform.
3. Publication remains auto-discovered. There is no publication manifest, central page registry, or hand-maintained list of works.
4. Auto-discovery is rooted only in allowed content zones and has explicit, tested exclusions for ignored, private, draft, and archive MDX.
5. Each source work is a bounded context under `content/works/{work}/`.
6. Sangram is a separate bounded context under `content/sangram/`.
7. Python tooling becomes one installable package, `sg_tooling`.
8. Pipelines are declared in versioned YAML and executed through package contracts.
9. Compact, reviewable data stays in Git. Large data stays outside Git and is referenced by immutable location, revision, checksum, and rights metadata.
10. `sanskrit-util`, VisualDCS, `csl-pyutil`, and WhitneyRoots remain canonical owners of their domains. SanskritGrammar consumes them through pinned adapters and does not fork their logic.
11. Migration is a hard cutover. Known consumers are coordinated for the same release; no compatibility directory, wrapper command, duplicate import path, symlink bridge, or deprecation period is retained.
12. Existing scholarly and data semantics are preserved: stable identifiers, source authority, editorial distinctions, attested/generated/traditional distinctions, review state, and provenance must survive moves.
13. TypeScript adoption is gradual and limited to touched site code or new site modules. It is not a prerequisite for the structural cutover.
14. `KnauerFrazy_1908` is the first work migration pilot.
15. SG-MO-021 “Future” is a later Sangram pilot, after the work pipeline and cutover mechanics are proven.

## 3. Observed current architecture

The current repository already contains several strong architectural choices:

- Docusaurus publishes the book site from repository content. The current configuration is visible in [docusaurus.config.mjs](https://github.com/gasyoun/SanskritGrammar/blob/main/docusaurus.config.mjs), and the autogenerated sidebar is defined in [sidebars.mjs](https://github.com/gasyoun/SanskritGrammar/blob/main/sidebars.mjs).
- Top-level directories containing MDX are auto-discovered. This fixed the earlier failure mode in which a converted work could be omitted from a static include list.
- Source works are recognizable as top-level contexts such as [KnauerFrazy_1908](https://github.com/gasyoun/SanskritGrammar/blob/main/KnauerFrazy_1908), [KocherginaUchebnik_1998](https://github.com/gasyoun/SanskritGrammar/blob/main/KocherginaUchebnik_1998), and [WhitneyGrammar_1889](https://github.com/gasyoun/SanskritGrammar/blob/main/WhitneyGrammar_1889).
- Sangram already has a distinct editorial and article area at [sangram](https://github.com/gasyoun/SanskritGrammar/blob/main/sangram).
- Python tests already protect many builders and scholarly checks in [tests](https://github.com/gasyoun/SanskritGrammar/blob/main/tests).
- Generated research data already exists in [data](https://github.com/gasyoun/SanskritGrammar/blob/main/data), while many work-local artifacts remain beside their owning work.
- The repository already consumes canonical sibling assets, notably Whitney source material from [WhitneyRoots](https://github.com/gasyoun/WhitneyRoots) and DCS data from [VisualDCS](https://github.com/gasyoun/VisualDCS).

The present shape is nevertheless a flat, convention-heavy repository:

- Site code, Python tooling, source documents, generated MDX, media, editorial data, and research outputs share the repository root.
- The current discovery rule starts at `.` and selects any top-level directory with a direct MDX child, then includes MDX recursively. The skip list protects selected technical directories, but ignored, private, draft, and archive paths are not a complete tested publication boundary.
- General builders, one-off research probes, Sangram generators, validators, and adapters coexist in `scripts/`; work-local scripts also occur inside work directories.
- Source and generated authority is inferred from filenames and documentation. For example, Word sources, generated MDX, hand-edited YAML, generated errata MDX, reports, and media may be adjacent without one machine-checkable ownership contract.
- Data is distributed among `data/`, `scripts/data/`, work directories, and Sangram article directories. Provenance pins and checksums are correspondingly distributed across scripts, prose, and output metadata.
- Sangram article JSON files currently carry article state. They must not become a second publication registry in the target design.
- Tests are predominantly a single flat suite, so unit, schema/contract, golden-output, and external-boundary failures are not visibly separated.
- Site tooling contains repository-layout assumptions and some machine-specific or sibling-path assumptions. That makes reuse and installation harder than importing a package contract.
- A change can preserve a successful site build while still moving or mutating scholarly semantics, because structural, golden, provenance, and source-authority gates are not yet one coherent system.

The modernization preserves what already works—Docusaurus, auto-discovery, Git review, deterministic builders, and bounded scholarly collections—while replacing implicit layout contracts with explicit ones.

## 5. Component boundaries

### 5.1 `apps/site`

`apps/site` owns presentation and publication:

- Docusaurus configuration, theme, React components, remark plugins, routes, and static assets;
- construction of a deterministic content include list from the allowed content zones;
- sidebar generation from discovered documents;
- broken-link, broken-anchor, MDX-compilation, and publication-exclusion gates;
- read-only consumption of generated work content and Sangram content.

The site does not convert Word files, query DCS, normalize Sanskrit, adjudicate claims, generate corpus tables, or mutate content during a build. A site build is a pure consumer of repository state. Content generation runs before the site build through declared pipelines.

The current site can move from JavaScript to TypeScript file by file. New configuration modules and new components should be TypeScript; existing React and remark modules convert only when touched or when a type boundary materially reduces publication risk.

### 5.2 `packages/sg_tooling`

`sg_tooling` is an installable Python distribution with both library and command-line interfaces. A clean environment must be able to install it and run `sg --help` without adding the repository root to `PYTHONPATH`.

Its internal layers are:

| Layer | Responsibility | Forbidden dependency |
|---|---|---|
| `cli` | Argument parsing, command dispatch, human-readable diagnostics, exit codes | No scholarly transformation logic |
| `domain` | Stable IDs, work model, provenance model, rights states, claim/errata rules, pipeline DAG semantics | No filesystem, network, subprocess, Docusaurus, or database access |
| `adapters` | Filesystem, YAML/JSON/TSV, DOCX/Pandoc, sibling-repository exports, SQLite, and external-object access | No hidden policy decisions |
| `generators` | Deterministic source-to-artifact transformations and validation orchestration | No direct access outside adapters |
| `contracts` | Versioned schemas, validators, serialization, compatibility rules for current contracts | No generator-specific side effects |

The public Python API exposes domain values and validated commands, not script internals. The public CLI uses stable verbs such as `sg work build`, `sg work check`, `sg pipeline run`, `sg provenance verify`, and `sg site discover`. Exact flags belong in the implementation document.

One-off research probes may remain executable modules, but they still enter through `sg_tooling` adapters and write declared outputs. A probe that becomes a repeated publication dependency must graduate into a generator with contract and golden tests.

### 5.3 `content/works/{work}`

Each work is a bounded context. It owns:

- its source witnesses and hand-maintained editorial files in `sources/`;
- its generated renderable documents and compact derived tables in `generated/`;
- its publication-safe images, diagrams, fonts, or other media in `media/`;
- its local identity, source authority, rights classification, transformations, outputs, and stable-route declarations in `work.yml`.

A work generator may depend on `sg_tooling` and declared external contracts. It may not import files from another work’s `sources/` or `generated/` by relative path. Legitimate cross-work studies consume exported stable contracts from `data/shared/` or a declared pipeline output.

`work.yml` is an operational work contract, not a publication manifest. The existence of `work.yml` does not include or exclude pages. Publication is determined only by the auto-discovery algorithm over allowed MDX zones.

### 5.4 `content/sangram`

Sangram is a bounded corpus-grammar publication context, not a synthetic “work.” It owns:

- the charter, evidence method, encoding method, program pages, and editorial guidance;
- article prose and article-local compact evidence;
- stable SG identifiers such as `SG-MO-021`;
- article generators that consume pinned corpus and lexicon contracts;
- preservation of distinctions among corpus-attested evidence, generated examples, traditional statements, negative results, kill-gates, and adjudication.

Current article-state JSON may be migrated into article-local evidence or provenance contracts where still scholarly necessary, but it is not consulted by site discovery. No replacement publication manifest is introduced.

### 5.5 `data`

`data/` owns repository-level, non-page artifacts:

- `provenance.lock.json`, the single machine-verifiable index of external immutable inputs;
- `shared/`, for compact cross-work contracts that have more than one in-repository consumer;
- `exports/`, for compact, versioned consumer feeds.

Work-local outputs remain inside their work. Article-local outputs remain inside the Sangram article. A file moves to repository-level `data/` only when its domain is repository-wide or it is an intentional export boundary.

### 5.6 `pipelines`

`pipelines/*.yml` declares reproducible build graphs. A pipeline manifest states inputs, commands, outputs, contract versions, provenance requirements, and verification steps. It does not contain executable Python or shell fragments.

The runner resolves registered `sg_tooling` command names rather than passing arbitrary strings to a shell. Pipeline manifests are orchestration declarations, not publication manifests.

### 5.7 `tests`

Tests are partitioned by failure meaning:

| Suite | Meaning |
|---|---|
| `unit` | Pure domain logic and small generator behavior |
| `contract` | YAML/JSON/TSV schema, stable IDs, source authority, rights values, pipeline graph, and discovery exclusion |
| `golden` | Byte-stable or semantically normalized expected outputs for representative works and Sangram articles |
| `integration` | Installed CLI, external adapters against fixtures, full pilot pipelines, and Docusaurus build |

Tests may share fixtures, but each gate has one primary failure category. This keeps a source-semantic regression distinguishable from a site rendering failure.

## 6. Core contracts and schemas

All schemas are versioned. Additive optional fields are allowed within a major version. Removing a field, renaming a field, changing identity semantics, or changing the meaning of an existing enum requires a major contract revision and a coordinated hard cutover.

### 6.1 Work contract

Minimum `content/works/{work}/work.yml` shape:

```yaml
contract_version: 1
work_id: work:knauer-frazy-1908
title: Knauer phrase collection
source_authority:
  primary: sources/Frazy-Knauer-03.05.2023.docx
  witnesses:
    - sources/Frazy-Knauer-03.05.2023.doc
rights:
  source: restricted-source
  generated_text: publishable
  media: per-file
stable_routes:
  primary: KnauerFrazy_1908/Frazy-Knauer-03.05.2023
transformations:
  - pipeline: work-knauer-frazy-1908
outputs:
  - generated/Frazy-Knauer-03.05.2023.mdx
  - generated/ERRATA.mdx
```

Required invariants:

- `work_id` never changes because a folder or title changes.
- Every source has an authority classification; “newest file” is not an authority rule.
- Every generated output has exactly one declared generator.
- A generated file cannot also be a source.
- Stable routes are preserved unless the plan explicitly authorizes a breaking public-route change.
- Rights are enumerated values validated by contract, not free prose interpreted by a build.
- Paths resolve inside the work root and may not escape through `..`, junctions, or symlinks.

### 6.2 Pipeline contract

Minimum `pipelines/work-knauer-frazy-1908.yml` shape:

```yaml
contract_version: 1
pipeline_id: pipeline:work-knauer-frazy-1908
context: work:knauer-frazy-1908
steps:
  - id: convert
    command: work.convert_docx
    inputs:
      - content/works/knauer-frazy-1908/sources/Frazy-Knauer-03.05.2023.docx
    outputs:
      - content/works/knauer-frazy-1908/generated/Frazy-Knauer-03.05.2023.mdx
  - id: errata
    command: work.build_errata
    needs:
      - convert
    inputs:
      - content/works/knauer-frazy-1908/sources/errata.yml
    outputs:
      - content/works/knauer-frazy-1908/generated/ERRATA.mdx
verification:
  - work.source_authority
  - work.golden
  - site.discovery
```

Required invariants:

- Step IDs are unique within a pipeline.
- The dependency graph is acyclic.
- Inputs and outputs are explicit and non-overlapping.
- No two pipelines claim the same output.
- Commands resolve to a registered CLI operation.
- A step cannot write outside its context except to a declared repository export.
- Output order, newline policy, encoding, and serialization are deterministic.
- A pipeline fails closed when a required provenance pin or rights assertion is absent.

### 6.3 Provenance lock contract

Minimum `data/provenance.lock.json` shape:

```json
{
  "contract_version": 1,
  "inputs": [
    {
      "id": "external:whitney-roots",
      "owner": "WhitneyRoots",
      "repository": "https://github.com/gasyoun/WhitneyRoots",
      "revision": "immutable-tag-or-full-commit",
      "path": "declared/export/path",
      "sha256": "64-lowercase-hex-characters",
      "bytes": 12345,
      "rights": "publishable-derived-input",
      "consumers": ["pipeline:declared-consumer"]
    }
  ]
}
```

For a large external object, `repository` may be replaced or supplemented by an immutable object URL, but `revision`, `sha256`, `bytes`, `rights`, and consumers remain required. Mutable branch URLs, “latest” downloads, local absolute paths, and undocumented sibling checkouts are not valid provenance.

The lock records identity and integrity; it does not transfer ownership or rights. The canonical owner remains responsible for upstream semantics.

### 6.4 Artifact identity contract

Stable identities are semantic, not path-derived:

| Entity | Form | Example |
|---|---|---|
| Work | `work:{slug}` | `work:knauer-frazy-1908` |
| Pipeline | `pipeline:{scope}` | `pipeline:work-knauer-frazy-1908` |
| Sangram topic | Existing SG code | `SG-MO-021` |
| Generated artifact | `{owner-id}#{local-id}` | `work:knauer-frazy-1908#primary-mdx` |
| External input | `external:{owner-or-dataset}` | `external:visualdcs-corpus` |

Existing public and scholarly IDs are preserved verbatim. A migration map records old path, new path, stable ID, source checksum, generated checksum, and route result. No path rename is allowed to silently create a new scholarly entity.

## 7. Source and generated authority

The target model has four authority classes:

1. **Authoritative source** — a primary witness, transcription, hand-maintained YAML/TSV, editorial prose, or adjudication decision that humans may edit.
2. **Generated artifact** — reproducible output of one declared pipeline; never hand-edited.
3. **Vendored snapshot** — compact external input copied into Git under an immutable pin and checksum; never silently refreshed.
4. **External pointer** — large or rights-restricted data not stored in Git; identified by immutable pointer and checksum.

The governing rules are:

- Fix an error at the highest authoritative layer that is actually wrong.
- Regenerate downstream artifacts; do not patch generated MDX, JSON, CSV, or HTML.
- Preserve original witnesses even when a normalized source is added.
- Record the exact generator version and external pins used for scholarly outputs.
- Generated output may be committed when compact, reviewable, and useful for diffs, offline builds, or citation stability.
- Large raw corpora, databases, scans, and model artifacts remain external unless rights and repository-size policy explicitly permit them.
- The site reads only publication-safe content. It never infers permission from the mere presence of a file in Git.
- Source checksums before and after migration are part of the cutover evidence.

## 8. Publication discovery and exclusion contract

### 8.1 Allowed zones

The Docusaurus include list is generated at configuration time from exactly two logical roots:

```text
content/works/*/generated/**/*.mdx
content/sangram/**/*.mdx
```

No MDX outside those roots is publishable. `docs/`, `data/`, `review/`, work `sources/`, test fixtures, generated review sheets, and external caches are outside the publication graph even if they contain valid MDX.

The generated include list is sorted by normalized POSIX path so builds are deterministic on Windows and Linux.

### 8.2 Exclusion algorithm

For each candidate MDX:

1. Resolve its real path.
2. Reject it if the real path is outside an allowed root or traverses a symlink or junction that leaves that root.
3. Normalize every path segment to Unicode NFC and compare case-insensitively.
4. Reject it if any segment is exactly `_ignored`, `ignored`, `_private`, `private`, `_draft`, `draft`, `drafts`, `_archive`, `archive`, or `archives`.
5. Reject it if the filename before `.mdx` ends in `.ignored`, `.private`, `.draft`, or `.archive`.
6. Parse front matter. Reject it if `draft: true`, `private: true`, `archived: true`, or `publish: false`.
7. Reject malformed front matter, duplicate document IDs, duplicate routes, invalid UTF-8, or a rights state that is not publication-safe.
8. Emit the remaining normalized paths to Docusaurus and the autogenerated sidebar.

This is auto-discovery, not a registry: adding a valid MDX under an allowed zone publishes it without editing configuration or a manifest. Exclusion is fail-closed and local to the path or document front matter.

### 8.3 Required discovery tests

Contract tests must prove:

- a new valid work MDX is discovered without configuration edits;
- a new valid Sangram MDX is discovered without configuration edits;
- MDX under each ignored, private, draft, and archive segment is absent;
- each excluded filename suffix is absent;
- each exclusion front-matter flag is absent;
- MDX under a work’s `sources/` is absent;
- MDX under `docs/`, `review/`, `tests/fixtures/`, and arbitrary new root directories is absent;
- a path traversal, escaping symlink/junction, duplicate ID, duplicate route, invalid rights value, or malformed front matter fails the build;
- discovery produces the same ordered list on Windows and Linux fixtures.

The test fixture contains at least one positive and one negative example for every rule. A successful Docusaurus build without these contract tests is not sufficient publication evidence.

## 9. Cross-repository ownership

SanskritGrammar may adapt canonical outputs, but it must not reimplement canonical logic.

| Concern | Canonical owner | SanskritGrammar contract | Prohibited in SanskritGrammar |
|---|---|---|---|
| Sanskrit transliteration, normalization, and shared string rules | [sanskrit-util](https://github.com/gasyoun/sanskrit-util) | Pin a released or immutable revision; call through a thin adapter; preserve scheme labels | New local transliteration tables, divergent normalization, copied helper modules |
| DCS ingest, corpus master, morphology/frequency derivation | [VisualDCS](https://github.com/gasyoun/VisualDCS) | Consume a documented compact export or immutable database pointer with checksum | Re-importing DCS into a second master or deriving a competing canonical frequency spine |
| Reusable Word/PDF-to-renderable-MDX and shared Cologne Python utilities | [csl-pyutil](https://github.com/sanskrit-lexicon/csl-pyutil) | Reuse released conversion primitives through an adapter; keep SanskritGrammar-specific postprocessing local | Vendoring another generic conversion shell or forking shared correction/transcoding utilities |
| Whitney grammar/root source data, root identities, and Whitney-derived canonical exports | [WhitneyRoots](https://github.com/gasyoun/WhitneyRoots) | Consume pinned exports; publish SanskritGrammar presentation artifacts with upstream provenance | Editing generated Whitney content as if SanskritGrammar were source authority or creating competing root IDs |
| Work editorial sources, work-specific transformations, site, Sangram prose, and SG stable IDs | [SanskritGrammar](https://github.com/gasyoun/SanskritGrammar) | Own locally under the boundaries in this document | Moving these decisions into a generic utility or external corpus owner |

Adapter code may translate shape, encoding, or path conventions, but it may not reinterpret upstream scholarly meaning without an explicit local derived artifact and provenance statement. If a reusable correction belongs upstream, the fix is made in the canonical owner and SanskritGrammar advances its pin.

## 10. Data placement policy

### 10.1 Keep in Git

Commit data when all of the following hold:

- rights permit repository storage and intended publication;
- it is compact enough for normal clone and review;
- text or structured diffs are meaningful, or the binary is an essential source witness;
- it has stable identity and documented authority;
- regeneration or acquisition is documented.

Typical examples are YAML editorial sources, small TSV/CSV/JSON contracts, golden fixtures, generated summary tables, MDX, and modest publication media.

### 10.2 Keep external

Store data externally when any of the following hold:

- it is a large corpus database, scan collection, model artifact, cache, or raw export;
- rights limit redistribution;
- it contains private review material or personal data;
- it is already canonically hosted by another repository or data provider.

Every external dependency must have an immutable revision or object identity, checksum, expected byte size, rights classification, and named consumer in `data/provenance.lock.json`. CI verification may use a cached object matching the lock. CI must not replace a missing immutable input with a mutable network fetch.

## 11. Pilot design

### 11.1 First pilot: `KnauerFrazy_1908`

[KnauerFrazy_1908](https://github.com/gasyoun/SanskritGrammar/blob/main/KnauerFrazy_1908) is the first pilot because it exercises the complete work boundary at manageable scale:

- legacy Word witnesses;
- one primary generated MDX;
- structured errata source and generated errata page;
- a work-local parse audit;
- stable public route requirements;
- source/generated distinction without a DCS-scale external dataset.

The pilot succeeds only if:

- authoritative source checksums match the pre-migration inventory;
- the work contract validates;
- the installed CLI regenerates byte-identical or semantically adjudicated outputs;
- old and new public routes match;
- ignored/private/draft/archive fixtures remain unpublished;
- the Docusaurus build and all four test suites pass;
- no active legacy script or duplicate output remains.

The pilot is performed on the target structure in the cutover branch. It does not create a compatibility period on `main`.

### 11.2 Later pilot: SG-MO-021 “Future”

SG-MO-021 “Future,” currently represented by [the Sangram future article](https://github.com/gasyoun/SanskritGrammar/blob/main/sangram/articles/future/index.mdx) and [its generator](https://github.com/gasyoun/SanskritGrammar/blob/main/scripts/sg_mo_021_future.py), is deliberately later.

It exercises a different boundary:

- stable SG identity independent of path;
- article prose plus generated corpus evidence;
- external VisualDCS provenance;
- negative or bounded claims and validation samples;
- Sangram editorial state without a publication manifest;
- article-local output ownership.

It must not be used to redesign the first pilot. It begins only after the Knauer work contract, pipeline runner, discovery boundary, and cutover process are verified.

## 12. Migration and hard cutover

The migration is prepared incrementally on a branch but released atomically.

### 12.1 Preparation

1. Inventory every tracked source, generated artifact, route, command, import, external input, and known consumer.
2. Record checksums, stable IDs, source authority, rights, and old public routes.
3. Define and test schemas before moving production content.
4. Make `sg_tooling` installable and port shared behavior behind contracts.
5. Prove the Knauer pilot and then the SG-MO-021 pilot on fixtures and real inputs.
6. Enumerate known consumers: repository workflows, documented local commands, Docusaurus, GitHub Pages, sibling repositories, and any downstream exported-data consumers.
7. Coordinate consumer changes for the same release window.

### 12.2 Cutover release

The cutover release:

- moves site files to `apps/site`;
- moves all work content to `content/works`;
- moves Sangram to `content/sangram`;
- moves active Python tooling into the installable package;
- installs declarative pipeline manifests;
- updates CI, npm commands, documentation, and known consumers;
- regenerates committed outputs through the new package;
- removes legacy scripts, root content directories, duplicate data, and obsolete article publication-state machinery;
- verifies route parity, source checksums, generated golden results, provenance locks, rights gates, and a clean Docusaurus build.

There is no interval in which both old and new commands or paths are supported on `main`. Documentation published with the cutover names only the new commands.

### 12.3 Consumer coordination

Known consumers receive one of two outcomes before merge:

- updated to the new path or export contract in the coordinated release; or
- explicitly retired with evidence that no supported workflow depends on it.

Unknown consumers are not a reason to preserve indefinite wrappers. The release notes provide the old-to-new path and command map, but that map is documentation, not executable compatibility.

## 13. Rollback semantics

Rollback preserves the hard-cutover rule:

- Before merge, rollback means abandoning or revising the cutover branch; `main` remains unchanged.
- After merge but before dependent data changes, rollback means reverting the complete cutover release and its coordinated consumer commits.
- After external pins or scholarly outputs advance, rollback uses the recorded source checksums and `provenance.lock.json` to restore the last coherent release as a unit.
- Partial rollback that restores old wrappers, mixes old and new generated outputs, or leaves two authorities active is forbidden.
- A failed generator never overwrites authoritative source. Generated directories are recreated from source and locked inputs.
- A rollback decision must state which release, provenance lock, routes, and consumer versions form the restored coherent set.

The system therefore has two supported states—complete pre-cutover and complete post-cutover—not a hybrid.

## 14. Security, privacy, and rights boundary

Security and rights are separate gates.

Security controls:

- pipeline commands are registered operations, not arbitrary shell text from YAML;
- all contract paths are normalized, bounded to an allowed root, and checked against traversal and escaping links;
- external objects are verified by checksum and byte size before parsing;
- parsers treat DOCX, YAML, JSON, TSV, MDX, archives, and databases as untrusted inputs with bounded resource use;
- generated MDX is checked for unsafe imports, scripts, remote embeds, and unexpected raw markup before publication;
- CI secrets are unavailable to content generation steps that do not need them;
- site builds do not require access to private source stores;
- review files and personal data are outside allowed publication zones.

Rights controls:

- every source, media file, external input, generated export, and publication artifact has a rights class;
- a technical ability to read or transform material is not publication permission;
- restricted sources may produce only outputs explicitly permitted by their rights and scholarly policy;
- full in-copyright text, rights-grey bulk glosses, private review HTML, credentials, and personal data do not enter site output or public exports;
- an absent, unknown, conflicting, or expired rights assertion fails closed;
- immutable pointers and hashes prove what was used but do not grant redistribution rights;
- attribution, license notices, and source citations survive generation and migration.

The publication boundary requires both a publication-safe rights value and success under the discovery algorithm. Neither gate substitutes for the other.

## 15. Preservation of scholarly semantics

Structural modernization must not flatten the repository’s intellectual distinctions. Contract and golden tests preserve:

- original-script text, transliteration scheme, normalization policy, Unicode composition, and significant punctuation;
- source page, section, lesson, sentence, token, lemma, root, and SG identifiers;
- distinctions among source transcription, editorial correction, normalized text, generated paradigm, corpus-attested example, traditional example, and analytic inference;
- errata state and the direction of correction;
- claim status, denominator, corpus universe, evidence pin, sample, adjudication, and kill-gate result;
- article publication and review history as scholarly metadata, while excluding it from discovery control;
- stable public routes and citation anchors;
- deterministic ordering and newline/encoding policy;
- upstream ownership and exact external revision.

Where byte identity is impossible because a generator is intentionally corrected, the migration records a reviewed semantic diff and updates the golden fixture in the same change. A directory move alone never authorizes wording, number, encoding, or identifier changes.

## 16. TypeScript adoption

TypeScript is adopted opportunistically:

1. New Docusaurus configuration helpers and discovery code are TypeScript.
2. Existing configuration files may convert during the site move.
3. Existing React components convert when edited for the migration or when they cross a new typed content contract.
4. Generated JSON consumed by the site receives generated or hand-maintained TypeScript types derived from the canonical contract schema.
5. JavaScript remains allowed during the transition if covered by tests.

Python remains authoritative for scholarly transformation and pipeline execution. TypeScript does not duplicate Python domain rules; it consumes serialized contracts or generated types. No all-at-once component rewrite is part of the architecture cutover.

## 17. Decisions and tradeoffs

| Decision | Benefit | Cost accepted |
|---|---|---|
| Modular monorepo | Atomic scholarly, tooling, site, and contract changes | Repository-wide CI and ownership discipline are required |
| Docusaurus retained | Preserves working publication, routes, components, and operator knowledge | Site remains a Node dependency alongside Python |
| Auto-discovery retained | New valid content appears without registry edits | Exclusion logic becomes security- and rights-critical |
| Allowed-zone discovery | Prevents accidental publication from arbitrary root directories | Content must move into a stricter tree |
| No publication manifests | Avoids stale include lists and competing publication authority | Discovery and front-matter validation must be rigorous |
| Per-work bounded contexts | Keeps source authority and generated outputs understandable | Similar work-local configuration may repeat |
| Installable `sg_tooling` | Testable imports, stable CLI, clean environments | Initial packaging and script migration cost |
| Declarative pipelines | Reviewable DAGs and reproducible outputs | A schema and runner must be maintained |
| Canonical external owners | Prevents duplicated Sanskrit and corpus logic | Builds depend on pinned upstream contracts |
| Compact Git data, large external data | Reviewable history without repository bloat | External-object availability and checksum management |
| Hard cutover | One supported architecture and no permanent migration debt | Higher coordination and rollback discipline |
| Gradual TypeScript | Improves site safety without delaying structural work | Mixed JS/TS persists temporarily |

## 18. Risks and mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Allowed-zone bug publishes private or draft MDX | Rights or privacy breach | Fail-closed algorithm, explicit fixtures for every exclusion, route inventory diff, publish-safety review |
| Hard cutover misses a consumer | Broken downstream command or import | Inventory from code search, CI, documentation, workflows, releases, and known downstreams; coordinated release and documented path map |
| Source and generated files are misclassified | Hand edits are lost or generated output becomes false authority | Work contracts, one-generator rule, source checksum inventory, migration review |
| Stable IDs drift during path moves | Broken citations and duplicate scholarly entities | Explicit ID contract, old-to-new migration map, duplicate-ID gate |
| Public routes change | Broken external links | Route parity golden test and Docusaurus crawl |
| External mutable input changes | Irreproducible claims or numbers | Immutable revision, checksum, byte size, offline fixture, lock verification |
| Upstream logic is copied locally | Divergent transliteration, corpus counts, or root identity | Ownership matrix, thin adapters, dependency audit |
| YAML becomes hidden executable code | Injection and non-reviewable behavior | Registered command enum; no shell fragments; bounded paths |
| Golden tests bless an accidental semantic change | False confidence | Source-level checks, normalized semantic diff, independent contract tests, human review for changed scholarly output |
| Large files enter Git | Clone and CI degradation | Size gate, storage policy, immutable external pointers |
| Mixed JavaScript and TypeScript creates friction | Two toolchains and uneven types | Touch-driven conversion, shared generated contract types, no duplicated domain rules |
| Cutover rollback becomes partial | Two active authorities and incoherent output | Whole-release revert only; lock and consumer-version coherence |
| Pilot is overfit to Knauer | Later corpus articles expose missing boundaries | Separate later SG-MO-021 pilot with VisualDCS and Sangram-specific acceptance |

## 19. Architectural acceptance

The architecture is realized only when all of the following are evidenced in the verification document:

- the target boundaries exist and legacy active paths are absent;
- `sg_tooling` installs in a clean environment and its public CLI runs;
- work, pipeline, provenance, rights, stable-ID, and artifact contracts validate;
- Knauer regenerates from authoritative sources through its declared pipeline;
- SG-MO-021 later regenerates through the Sangram boundary with its external provenance intact;
- source checksums and reviewed semantic diffs account for every moved authoritative file;
- committed generated outputs match golden expectations;
- Docusaurus auto-discovers valid new MDX in both allowed zones;
- all ignored, private, draft, archive, source, review, and arbitrary-root MDX fixtures remain unpublished;
- public routes and anchors meet the approved parity policy;
- canonical sibling ownership is preserved and no duplicate transliteration, DCS ingest, generic conversion, or Whitney-root authority is introduced;
- known consumers are updated or retired in the same cutover;
- unit, contract, golden, integration, security, rights, and site-build gates pass;
- rollback to the last coherent release is documented and rehearsed without compatibility shims.
