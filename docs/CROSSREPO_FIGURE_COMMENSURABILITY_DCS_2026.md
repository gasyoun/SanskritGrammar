# Cross-repo figure commensurability — which DCS-2021 numbers may be compared with VisualDCS

_Created: 06-08-2026 · Last updated: 06-08-2026_

The adjudication record behind check 3 of
[`scripts/check_claims_consistency.py`](https://github.com/gasyoun/SanskritGrammar/blob/main/scripts/check_claims_consistency.py)
([H2298](https://github.com/gasyoun/Uprava/blob/main/handoffs/archive/H2298-Opus_SanskritGrammar_crossrepo-figure-consistency-gate_05.08.26.md)).
It exists because **the rejected pairs are the finding**: a gate seeded with one
incommensurable pair fires false alarms, and the standing response to a noisy blocking gate
is to switch it off. Read this before adding a row to `CROSS_REPO_FIGURES`.

## What the gate compares

VisualDCS publishes its headline DCS-2021 figures as a committed contract asset,
[`dcs_published_figures.json`](https://github.com/gasyoun/VisualDCS/blob/main/dcs_published_figures.json)
(generated by `regen_widgets.py --figures-only`). We vendor a copy at
[`data/dcs_published_figures.json`](https://github.com/gasyoun/SanskritGrammar/blob/main/data/dcs_published_figures.json)
— a GitHub workflow checks out ONE repo, so the gate cannot read a sibling clone.

Our side is **not** a hand-copied restatement of theirs. It is
[`KocherginaUchebnik_1998/claims_dcs_stats.json`](https://github.com/gasyoun/SanskritGrammar/blob/main/KocherginaUchebnik_1998/claims_dcs_stats.json),
the committed output of our own
[`verify_claims_dcs.py`](https://github.com/gasyoun/SanskritGrammar/blob/main/KocherginaUchebnik_1998/verify_claims_dcs.py),
which reads the same primary source (`timws.csv`) independently. Both sides derive; the gate
compares two derivations. A pin of a copy against a copy would only ever detect a publisher
edit — this detects a genuine disagreement about the corpus.

| All verbal examples | 781,618 | all 42 | `total_verbal_tokens` | Both are the full-code sum. Carries a **tolerance of ±10** — see below. |

All five are `unit: tokens` over the same basis: *DCS-2021 verbal examples, all 42 timws.csv
tense/mood codes, summing to 781,618*.

### The one tolerance, and why it is not a fudge

`timws.csv`'s 42 codes sum to **781,618**; `README.md`/`CLAUDE.md` document **781,616** from
the Excel source. The ±2 is a real, documented source-side difference (see
`read_2021_verbcats` guard 2 in `regen_widgets.py`), not drift. Pinning it exactly would make
the gate fail on a known fact — the fastest route to a gate being switched off. Tolerance is
±10, wide enough for the documented delta and far too narrow to hide any real divergence
(the smallest failure this gate is built to catch is 35,921).

## Rejected pairs — the finding

### 1. Imperfect (all codes) vs `Imperfect Active` — REJECTED as originally posed

This is the trap the handoff walked into, and the most important row here.

Our `HK15_past_tenses.imperfect_tokens` is **47,554** = codes 4 + 8 + 9 + 16 + 27, i.e.
imperfect **active + medium + augmentless + passive**. VisualDCS's `Imperfect Active` is
**40,363** = codes 4 + 8, active only. Both numbers are correct. They are not the same
quantity, and seeding them as a pair would have produced a permanent 7,191-token false alarm
on day one — the exact failure mode that gets a blocking gate disabled.

H2298 assumed `verify_claims_dcs.py` already held 40,363 (`TOK[4] + TOK[8]`). It did not; it
held the five-code sum. **Resolution:** rather than drop the headline pair, we added
`imperfect_active_tokens` (codes 4+8) to `verify_claims_dcs.py` beside the existing five-code
figure. Our repo now derives *both*, and only the two-code one is wired to the contract. The
five-code figure keeps its own consumers (the past-tense competition claim) untouched.

### 2. DCS-2021 figures as `claims.yml` citation captures — REJECTED (scope)

The obvious-looking extension — folding the published values into `CONSISTENCY_FIGURES` so
`*/claims.yml` prose is checked against them — was considered and **rejected**, on two counts:

- **It would weaken the existing gate.** `CONSISTENCY_FIGURES` is standardised on **DCS-2026**
  (perfect 90,001 · imperfect 46,695 · present 353,215 · denominator 523,738). Adding the
  DCS-2021 vintage values to those same figure names would widen each `allowed` set, so a
  register citing the superseded 61,986 where 90,001 is required would start passing. A
  cross-repo check must not buy reach by loosening an intra-repo check.
- **The one non-colliding candidate is too brittle to be worth it.** The live aorist-voice
  citation ([`ZalizniakOcherk_1978/claims.yml`](https://github.com/gasyoun/SanskritGrammar/blob/main/ZalizniakOcherk_1978/claims.yml),
  "act 1,304 vs med 1,148") has no DCS-2026 name collision, but any regex tight enough to
  match it is tight enough to break on innocent rewording — a false alarm caused by editing
  prose, not by drifting a number.

Check 3 therefore compares **derived asset against derived asset**, which is where the H2293
divergence class actually lives. Claims-register prose stays with checks 1 and 2.

### 3. Types-vs-tokens pairs — REJECTED categorically

`15.csv` / `12.csv` are **distinct-form (type)** tables; `timws.csv` is **tokens**. Several
figures exist in both flavours (aorist: 2,452 tokens vs a distinct-form count; PPP; future).
No type figure is seeded, and `unit` is mandatory on every published row precisely so such a
pair is refused mechanically rather than by memory. A type/token confusion is the single most
likely way a wrong pair enters this table.

### 4. DCS-2026 figures — REJECTED (out of scope, deliberately)

The 2026 master (`dcs_full.sqlite`) has different denominators (523,738 finite verbal forms)
and a re-split past tense whose Aorist is a **lower** bound and Perfect an **upper** bound
(H1486 — see `reports/past_tense_resplit_validation.md`). Bounds are not exact counts and
must not be gated as if they were. This is two repos and one seeded list, per the handoff's
non-goals.

## How a pair gets added

1. Confirm both sides read the same primary source and the same **code set**.
2. Confirm the same `unit` and the same `basis` (denominator).
3. Publish the row from VisualDCS with `source_codes` explicit.
4. Add it to `CROSS_REPO_FIGURES` with `expect_codes` pinned, and add a row to the accepted
   table above with the commensurability argument.
5. Confirm `test_planted_divergence_in_each_seeded_pair_is_caught` still passes — every
   seeded row must be load-bearing.

`expect_codes` is the commensurability lock: if VisualDCS republishes a figure over a
different code set, the gate reports **`incommensurable`**, not `drift`. That distinction is
deliberate — "drift" invites a maintainer to edit a number until it matches, which is the
wrong fix when the two sides have stopped measuring the same thing.

## Known residue

- `verify_claims_dcs.py` iterates Python `set`s when building two suffix-split `Counter`s, so
  regenerating `claims_dcs_stats.json` reshuffles key order in `HK3_gerundive.suffix_split_types`
  and `HB_absolutive_allomorphy.suffix_split_types`. Values are stable; only ordering churns.
  Cosmetic diff noise in a numbers-gate repo — filed as a papercut, not fixed here.
