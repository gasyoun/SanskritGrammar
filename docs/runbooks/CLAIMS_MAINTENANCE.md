# Claims register maintenance — runbook

_Created: 27-07-2026 · Last updated: 27-07-2026_

> **Fence, read first:** `<Book>/CLAIMS_VERIFIED.md` and the root claims index are
> **generated** from `<Book>/claims.yml` — never hand-edit the generated files. Corpus
> numbers come from each book's own `verify_claims_dcs.py` (or its book-specific
> equivalent) — never invent a number; reuse an existing JSON/TSV metric or rerun the
> script that produced it.

Claims (`claims.yml`) are a **distinct register from errata** (`errata.yml`, see
[MONTHLY_ERRATA.md](https://github.com/gasyoun/SanskritGrammar/blob/main/docs/runbooks/MONTHLY_ERRATA.md)):
errata catalogue *typos in the print*; claims catalogue *falsifiable grammatical
assertions* graded on two axes — `verdict_fact` (TRUE / OVERSTATED / FALSE /
UNTESTABLE / PENDING) and `verdict_pedagogy` (JUSTIFIED / MISLEADING / RARE-AS-CENTRAL /
FREQUENCY-HIDDEN / ORDER-QUESTIONABLE).

## When to rebuild vs. check

| Command | When |
|---|---|
| `npm run claims` (`python scripts/build_claims.py`) | after editing any `claims.yml` (new verdicts, promoted harvest candidates, corrected numbers) — regenerates every book's `CLAIMS_VERIFIED.md` + the root index. Pass one book directory to regenerate only that book. |
| `npm run check-claims` (`python scripts/check_claims_consistency.py`) | before committing any `claims.yml` change, and as a standing CI/pre-commit guard — catches figure drift, not just build errors. Exit 0 = clean, 1 = drift found. |

`check-claims` runs two checks over every `*/claims.yml`:

1. **Supersession** (`CANONICAL_FIGURES`) — a value that was recomputed and replaced
   must not silently reappear as a live number (e.g. the old DCS-2021 tense-code aorist
   count vs. the later feat_formation recount).
2. **Consistency** (`CONSISTENCY_FIGURES`) — the same quantity reused across registers
   must carry one live value everywhere. A block with a correction marker
   (`refreshed`, `undercounted`, `older …`, a version tag) is exempt — it's documented
   history, not a live citation.

Wired into CI via `tests/test_claims_consistency.py` — a `claims.yml` edit that breaks
either check should fail before it ever reaches a PR.

## Per-book verify scripts

Corpus figures cited in a `claims.yml` are reproduced by that book's own
`verify_claims_dcs.py` (present for `BuhlerLeitfaden_1923`, `KocherginaUchebnik_1998`,
`ZalizniakKonspekt_2004`, `ZalizniakOcherk_1978` as of this writing — verify live with
`Glob('*/verify_claims_dcs.py')`, do not assume the list is stable). Run the relevant
book's script to reproduce or extend a metric rather than hand-computing a new number
inline in `claims.yml`.

Two books use a variant instrument instead of the standard verify script, because their
source genre doesn't fit the discursive-grammar claim shape:

- **`KnauerFrazy_1908`** — a phrase reader, not a discursive grammar; uses
  `parse_audit.yml` + `PARSE_AUDIT.md` (via `build_parse_audit.py`) to audit individual
  footnote morphological parses against Whitney, instead of grading universality/
  frequency prose.
- **`ZalizniakMorphology_1975`** — a scholarly root-classification paper, not a
  textbook; uses `build_root_classifier.py` + `root_classifier.json` +
  `ROOT_CLASSIFICATION_AUDIT.md` to cross-check its named roots against
  [`WhitneyRoots/crosswalk/roots.csv`](https://github.com/gasyoun/WhitneyRoots/blob/main/crosswalk/roots.csv),
  rather than a claim-by-claim verdict register.

`GasunsDhatu_2014` and `TolchelnikovTalmud_2026` have no `claims.yml` as of this
writing — verify live before assuming that's still true.

## Harvest promotion rule

Bulk-harvested candidate claims live in each book's `claims_harvest.yml`
(`candidates:` list), separate from the verified `claims.yml`. A candidate is promoted
by:

1. Verifying it (reference grammar and/or the book's `verify_claims_dcs.py` /
   equivalent instrument).
2. Adding it to `claims.yml` with a stable `<PREFIX>-N` id and both verdict axes filled
   in.
3. Marking the source row in `claims_harvest.yml` with `promoted: <PREFIX>-N` — it stays
   in the harvest file for provenance, it is never deleted.

`build_claims.py`'s `load_harvest()` reads `claims_harvest.yml`, drops anything already
marked `promoted`, and renders the remainder as the book's backlog section in
`CLAIMS_VERIFIED.md` — so an unpromoted candidate is visible on every rebuild without
manual bookkeeping. Never promote a candidate by editing `CLAIMS_VERIFIED.md` directly;
the `promoted:` marker in `claims_harvest.yml` is the only mechanism `build_claims.py`
respects.

## Generated-file fence (repeat)

`<Book>/CLAIMS_VERIFIED.md` and the root claims index are generated by
`scripts/build_claims.py` — never hand-edit them. If a verdict or number is wrong, fix
`claims.yml` (or the `verify_claims_dcs.py`/equivalent instrument that produced the
number) and rerun `npm run claims`.

## Fence: no invented corpus numbers

Every corpus figure in `claims.yml` must trace to a reproducible instrument — that
book's `verify_claims_dcs.py` (or `build_root_classifier.py` / `build_parse_audit.py`
for the two variant books) — or to a JSON/TSV artifact that instrument already wrote.
Do not hand-type a percentage or count into `claims.yml` without a script run backing
it; `check-claims` cannot catch a number that was simply made up rather than drifted.
